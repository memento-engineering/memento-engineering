# Org CLIs ship through one Homebrew tap, stable releases only

## Context and Problem Statement

`decisions#the-decisions-cli-ships-as-prebuilt-binaries` makes the `decisions` CLI the first org
tool released as native binaries. The other Dart CLIs on the roster are candidates to follow. Each
could stand up its own tap, its own formula conventions and its own bump credential, or they can
share one. A tap is also an install channel, so it has to respect the line the org already draws
between agent-published prereleases and human-promoted stable versions
(`agents-publish-prereleases-humans-promote-to-stable`).

## Considered Options

* **The releasing repo pushes the bump** from its release workflow, with a token scoped to the tap.
* **The tap polls** each CLI's releases on a schedule and bumps itself with its own token, needing
  no secret. GitHub disables a public repo's scheduled workflows after 60 days without activity,
  so the poller would stop silently in exactly the quiet periods between releases.

## Decision Outcome

**The org has one Homebrew tap, `memento-engineering/homebrew-tap`.** Any org CLI that ships
prebuilt binaries is installed as `brew install memento-engineering/tap/<executable>`, with one
formula per executable, named after it.

1. **Stable releases only.** A formula moves only on a non-prerelease tag, which is a human
   promotion. Prereleases stay on GitHub Releases, where they can be pinned by version and checksum.
2. **The tap is output.** Each formula is generated by the repo that releases the CLI, from that
   release's own checksums, and pushed by its `.github/workflows/release.yaml`. Nobody edits a
   formula in the tap by hand; the next release would overwrite it.
3. **One narrow credential.** The bump uses the org secret `HOMEBREW_TAP_TOKEN`: a fine-grained
   token with contents read and write on `homebrew-tap` only, shared with selected repos. A repo
   that starts releasing to the tap is added to the secret's repository list. Nothing else may use
   it.

### Consequences

* Good, because adopters learn one install line for every org CLI, and the tap only ever offers
  versions a person promoted.
* Good, because a formula can never disagree with the release it names: both come from the same
  checksums in the same workflow run.
* Bad, because the token belongs to a person's account and expires. When it lapses the bump job
  fails visibly and the formula stays at the previous stable version until it is rotated.
* Bad, because the tap only covers platforms a CLI builds for; a formula for a CLI without an Intel
  Mac binary refuses to install there rather than falling back to source.
